# Search Engine Tool — COMP3011 Coursework 2


A command-line search engine built in Python that crawls [quotes.toscrape.com](https://quotes.toscrape.com/), builds an inverted index, and allows full-text search with TF-IDF ranked results.

---
## Project Overview

This tool builds a complete search engine from scratch. It crawls every page on [quotes.toscrape.com](https://quotes.toscrape.com/), indexes all the words it finds, and lets you search through them using a command-line interface.

The three main components are:

- **Crawler** — visits every page on the site using BFS (Breadth First Search), following links and respecting a 6 second delay between requests
- **Indexer** — takes the crawled pages and builds an inverted index that stores where each word appears and how often
- **Search Engine** — lets you search the index and returns results ranked by TF-IDF score, so the most relevant pages appear first

On top of the basic requirements, the tool also includes query suggestions, execution timing for every command, and a help command, which are explained in detail further below.

## Advanced Features

### Query Suggestions
The `suggest` command lets you find words in the index by typing just the beginning of a word. It returns up to 5 matches sorted alphabetically, along with how many pages each word appears on. This is useful when you are not sure of the exact spelling of a word.

### Help Command
The `help` command shows all available commands and what they do, making the tool easier to use for someone running it for the first time.

### TF-IDF Ranked Results
Instead of just returning a list of pages that contain a word, results are ranked by TF-IDF score so the most relevant pages appear first. Term frequency is also normalised by document length so longer pages don't unfairly dominate the results.

### Optimised Search
Three optimisations were applied to make search faster:
- **IDF caching** — IDF values are calculated once when the index loads, not on every search
- **Rarest-first intersection** — for multi-word queries, the word with the fewest results is always processed first to keep intermediate result sets small
- **Query deduplication** — if the same word appears twice in a query it is only processed once

### Formatted Output
All commands produce clean tables with borders, column headers and numbered rankings so results are easy to read.

### URL Normalisation
The crawler treats `/page/2`, `/page/2/` and `/page/2/?sort=asc` as the same URL so no page gets crawled twice.

### Boilerplate Removal
Nav menus, footers, headers, scripts and styles are stripped from pages before indexing so only the actual content gets indexed.

## Data Structures

The inverted index uses a dictionary of dictionaries, an example from ` index.json `:

```python
{
  "word": {
    "https://quotes.toscrape.com/page/1/": {
      "frequency": 3,
      "positions": [5, 23, 47]
    }
  }
}
```

This gives O(1) lookup by word and O(1) lookup by document. A simpler dictionary of lists was considered but rejected because it can't store per-document statistics, which are needed for TF-IDF ranking.

## Algorithm Complexity Analysis

### Crawling
- **Time:** O(P × L) where P is the number of pages and L is the average number of links per page
- **Space:** O(P) for keeping track of which pages have been visited
- BFS makes sure every page is found and none are visited twice

### Indexing
- **Time:** O(P × W) where W is the average number of words per page
- **Space:** O(V × D) where V is the number of unique words and D is the number of pages
- Looking up any word or any page in the index is O(1)

### Searching
- **find:** O(Q × D) where Q is the number of query words and D is the number of matching pages
- Query words are sorted by how many pages they appear in, so the rarest word is always processed first, this keeps the intermediate results small
- IDF values are calculated once when the index loads so each lookup during search is O(1)
- **print:** O(D) where D is the number of pages the word appears in

## Design Decisions

### Crawler
- Used BFS so every page gets found in a systematic order
- The 6 second politeness window is required by the brief
- URLs are normalised by removing query parameters, fragments and enforcing trailing slashes, this stops the same page being crawled twice with slightly different URLs
- Used `collections.deque` instead of a regular list for the queue because `popleft()` is O(1) rather than O(n)
- Kept a separate set of queued URLs so duplicates never enter the queue at all
- Added a User-Agent header so the crawler identifies itself properly
- mailto, javascript and anchor links are filtered out since they can't be crawled

### Indexer
- Script, style, nav, footer and header tags are removed before indexing so they don't pollute the results
- Everything is lowercased so Good and good are treated as the same word
- Word positions are stored alongside frequency in case phrase search is added later
- The number of tokens per page is stored so TF can be divided by document length

### Search
- Results are ranked by TF-IDF so the most relevant pages come first
- TF is divided by document length so longer pages don't always rank higher
- IDF values are calculated once when the index loads rather than on every query
- If the same word appears twice in a query it is only counted once
- For multi-word queries the rarest word is always intersected first
- The suggest command lets you find words by typing just the start of them
- Every command shows how long it took so you can see the performance in real time

### Known Limitations
- Common words like the, is and to are not removed, which keeps the index simple
- Numbers are not indexed so years and dates won't appear in results

## Performance Benchmarking

### Build Performance
- Pages crawled: 213
- Total build time: 1368.2 seconds (~23 minutes)
- Each page takes around 6 seconds due to the politeness window, plus a small amount of time for the actual network request and HTML parsing
- The final index contains 4324 unique words across 213 pages

### Search Performance
All search operations are timed and shown directly in the terminal when you run a command. These are the actual times recorded on a MacBook:

| Operation | Time |
|---|---|
| `load` index from disk | 0.079s |
| `print` single word | 0.0017s |
| `find` single word (11 results) | 0.0020s |
| `find` multi-word query (3 terms) | 0.0066s |
| `suggest` prefix lookup | 0.0022s |

Every search completes in under 5 milliseconds. This is because the index uses dictionary lookups which are O(1), IDF scores are calculated once at startup rather than on every query, and multi-word searches always start with the rarest word to keep the result set small from the beginning.

## GenAI Reflection — Copilot

I used Copilot throughout this project. Below is a critical evaluation of its impact on my development process.

### Where Copilot Helped

- It identified that my crawler was using list.pop(0) which is O(n) and suggested using collections.deque which gives O(1) operations, I implemented this fix and added tests to verify it
- It confirmed that dictionary of dictionaries was the right data structure for the inverted index, which matched my own research into search engine design
- It helped me understand core concepts like BFS crawling and inverted index structure early in the project before I started writing code

### Where I Went Beyond Copilot

- Copilot described word frequency and positions as optional enhancements, but I implemented both because they are essential for TF-IDF ranking which is a core part of my implementation
- Copilot generated tests that missed important edge cases including malformed HTML, non-HTTP links and URL normalisation, but I identified these gaps myself and added the missing tests
- Copilot initially suggested a simpler dictionary of lists for the inverted index, but I rejected this because it cannot store per-document statistics needed for ranking

### Learning Reflection

- Copilot was most useful as a code reviewer rather than just writing code
- Critically evaluating every suggestion deepened my understanding of the code more than blindly accepting them would have
- All AI usage has been declared and every line of code is fully understood and justifiable
